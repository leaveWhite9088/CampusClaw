实现教程

CampusClaw 是面向中小学的教研智能体。本迭代先搭建它的底座：登录与角色权限、班级数据边界、教研材料上传与知识库入库。本课交付第 2 课那个 change 的实施、校验与归档；每一页先读知识点，再看动手步骤。

本课在项目中的位置

完整形态覆盖学情分析、备课、命题、课堂与教研协同。本课只交付迭代 1：教研材料与知识库底座，也就是后续智能能力的地基。因此判定标准不是界面是否好看，而是：能登录、能隔离、能上传入库、第三方能按 README 复现。

1术语约定：Harness

本课从头到尾用它指代“按规约改代码的那一方”。先给出准确释义，后续各页直接使用。

知识点

Harness：驱动并约束模型的那层系统

Harness 原义“挽具”——套在马上、把牵引力导向农具的整套革带。AI 编程沿用了这个比喻：Harness 指使模型能够作为智能体行动的那层系统——把输入交给模型、编排工具调用、把运行结果回传，直到任务结束。业界常见概括：“除了模型，其余都是 harness。”

所以 Harness 不包含模型本身——模型是引擎，harness 是套在外面的那层：给模型的指令与约束（系统提示、AGENTS.md、change 四件套）、可调用的工具（读写文件、执行命令）、以及循环与边界（权限限制、结果回传）。Cursor、Codex、Claude Code 都是 harness；同一个模型配不同 harness，行为差异主要来自 harness。

写规约能约束生成，机制就在这里：AGENTS.md 与 change 四件套本身就是 harness 的一部分，不是给模型的“参考意见”。

哪些交给它，哪些必须由你负责

环节 Harness 负责 必须由你负责
范围 在给定规约内把功能实现出来 范围由 proposal.md 与 Non-goals 决定，不随其超出规约的自发改动而扩张
依据 先读 design.md 与 delta spec，再动手改代码 规约含糊或缺失时先改规约，而不是由它自行裁量
判定 执行命令，给出运行输出 “是否合格”由 Scenario 与运行结果判定，不由它自己下的结论判定
责任 按你的驳回理由重做 提交人对产出负责，审查责任不因使用工具而转移
记住这一条：把规约交给 Harness，是为了让它按字面实现。若它额外生成了规约中未声明的功能，问题通常出在规约缺了“不做”的条目——先补规约，再删代码。

3本课在 OpenSpec 中的位置

第 2 课把需求写成了 change 的四件套；本课是同一个变更的后三步：实施、校验、归档。

知识点

一次变更 = 一个 change

OpenSpec 把规约做成仓库里的一等工程制品：openspec/changes/<change>/ 下的四份 Markdown 就是这次变更的全部依据。流程围绕这四份文件推进，不围绕对话。

一次变更走五步：提变更（Propose）→ 评审（Review）→ 实施（Apply）→ 校验（Verify）→ 归档（Archive）。第 2 课做完前两步，本课做完后三步。

四件套各管一段：proposal.md 说为什么做、明确不做什么；design.md 说怎么做；specs/<capability>/spec.md 用 Requirement 与 Scenario 说「做到什么算合格」；tasks.md 把实现拆成一条条带 verify 的待办。

本课在五步中的位置

步骤 做什么 产物 本课
Propose 提变更 把需求写进 change，不允许只停留在对话里 四件套初稿 第 2 课
Review 评审 交叉阅读：范围对不对、每条要求能否判定 修订后的四件套 第 2 课
Apply 实施 按 tasks.md 逐项实现，完成一项勾一项 代码 + 勾选后的 tasks.md 本课做
Verify 校验 结构校验 + Scenario 逐条判定 validate 通过、验收证据 本课做
Archive 归档 delta 合并进主力规约，change 移入归档目录 openspec/specs/ 更新 本课做
本课的边界：只动 change 目录。openspec/specs/ 是长期事实来源（source of truth），只由归档更新。Apply 期间发现规约要改，改的是 change 里的 delta（specs/<capability>/spec.md），不是主力规约——一旦回写主力规约，delta 就失去比对基线，归档时也就无法判断这次究竟改了什么。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
本人 change 目录是否四件套齐全？ 齐全：proposal.md、design.md、tasks.md、specs/<capability>/spec.md。 规约：openspec/changes/<change>/ 下四文件齐全（演示仓 change 名 add-auth-rbac-class-knowledge：proposal.md、design.md、tasks.md、specs/auth-upload/spec.md）
代码：仓库里 change 目录的实际文件
运行：openspec list 能看到本 change
本能力是否还没出现在主力规约里？ 还没出现。openspec/specs/ 只由归档更新；若已出现，说明有人提前回写了主规约。 规约：proposal.md 的 Modified Capabilities 与 openspec/specs/ 归档约定
代码：看 openspec/specs/ 下的目录
运行：openspec list --specs，本能力应不在其中
tasks.md 的待办是否仍全部未勾选？ 第 2 课交付时全部是 [ ]；勾选从本课第一项 task 才开始。 规约：openspec/changes/<change>/tasks.md 开工前全部为 [ ]
代码：打开 tasks.md 看方括号
运行：统计已勾选项数量，开工前应为 0

动手要做

  • 在学期仓根执行 openspec list，确认本 change 在活动列表中。
  • 执行 openspec list --specs，确认主力规约里还没有本能力——它要等归档之后才出现。
  • 打开 openspec/changes/<change>/，通读四件套：proposal.md（范围与 Non-goals）、design.md（决策与接口）、specs/auth-upload/spec.md（Requirement / Scenario）、tasks.md（顺序与 verify）。讲师规约 / Apply 起点：AI-DevOps/project-src/week03/；Apply 完成可运行对照：AI-DevOps/project-src/week03-applied/。

4三个必须记住的判断

全课的知识基础。后面每一步的核对，都在验证这三条是否落进了规约与代码。

知识点

规约是契约，代码是派生物

vibe coding（对话式即兴生成）以对话为准，SDD（Spec-Driven Development，规约驱动开发）以规约为准。本课的驳回、验收与质量门禁（gate）都来自这个区别。Harness（AI 编码代理）生成的代码若偏离规约，应引用 Scenario（场景）驳回，而不是通过追加对话不断扩大范围。

认证、授权、隔离是三件不同的事

认证回答你是谁；授权回答你能做什么；隔离回答你能看见哪一块数据。缺会话属性（用户、角色、班级）时，后面的需求无法判定。

访问控制必须在服务端强制执行

Saltzer（杰罗姆·萨尔策）与 Schroeder（迈克尔·施罗德）在 1975 年论文《计算机系统中的信息保护》（The Protection of Information in Computer Systems）中提出的安全设计原则：默认拒绝（Fail-Safe Defaults）、最小权限（Least Privilege）、每次请求完整校验（Complete Mediation）。前端隐藏按钮只降低可发现性，不构成访问控制。对应威胁：垂直越权（BFLA，Broken Function Level Authorization，学生调用教师专属接口）与水平越权（BOLA / IDOR，Broken Object Level Authorization / Insecure Direct Object Reference，同角色访问其他班级数据）。

5交付纪律：三条被否决的做法

这三种做法都会让“实现是否可判定”失去依据，因此本课明确否决。

其他可行方案与选择依据

方案 要点 本课如何取舍
vibe coding 一次生成 对话即需求，速度快，但规约与验收标准难以保持一致。 否决。本课用 SDD：规约是契约，代码是派生物。
只写规约不发布 设计完整但第三方无法启动。 否决。本课要用 Compose 交付迭代 1 的成果。
分组共用仓库 协作快，责任不清。 否决。个人独立提交，互验用同伴交叉验证。

把否决理由用自己的话写进 design / 迭代说明。原文照录本表不算 ADR（Architecture Decision Record，架构决策记录）。

本课要交付什么

用 Docker Compose 在本机启动一个可登录、可隔离、可上传入库的 CampusClaw 基础版本。这一版只做教研材料与知识库底座，智能备课、智能命题、学情诊断等能力留待后续迭代。验收以本人学期仓库中的 OpenSpec 规约为准；技术栈若与第 2 课 design 不一致，先改规约再实现。

要做成什么样登录权限、隔离、材料与页面体验 系统怎么走浏览器 → Nginx → Go → MySQL 安全与部署哈希、Cookie、环境变量、Compose 认证方案对照会话、JWT、Refresh、OAuth 的取舍 实现路线图八步，一步一轮，不要一次性生成全站 实现方案核对总表八步决策点汇总，可打印后逐项勾选
请独立完成、独立提交。本教程按当前需求描述编写，不是作业提交系统，也不提供可整体复制仓库的参考实现。

想一想：判断与取舍

先对照本人规约作答。引用不到原文，先改规约再写代码。

  • 本人规约里，未登录访问受保护接口时，是否写明响应不得含材料标题或正文？只写跳转登录页够不够？
  • 本课只做迭代 1。本人规约的 Non-goals（明确不做项）是否写清？若没写，Harness 会替你把哪些越界功能“补”进来？
  • 若把登录态从服务端会话（session）换成 JWT（JSON Web Token），本课哪几条验收会变成无法判定？为什么？
