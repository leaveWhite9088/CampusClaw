## 实现教程

CampusClaw 是面向中小学的教研智能体。本迭代先搭建它的底座：登录与角色权限、班级数据边界、教研材料上传与知识库入库。本课交付第 2 课那个 change 的实施、校验与归档；每一页先读知识点，再看动手步骤。

### 本课在项目中的位置

完整形态覆盖学情分析、备课、命题、课堂与教研协同。本课只交付**迭代 1：教研材料与知识库底座**，也就是后续智能能力的地基。因此判定标准不是界面是否好看，而是：能登录、能隔离、能上传入库、第三方能按 README 复现。

### 1. 术语约定：Harness

本课从头到尾用它指代“按规约改代码的那一方”。先给出准确释义，后续各页直接使用。

#### 知识点

#### Harness：驱动并约束模型的那层系统

**Harness** 原义“挽具”——套在马上、把牵引力导向农具的整套革带。AI 编程沿用了这个比喻：**Harness 指使模型能够作为智能体行动的那层系统**——把输入交给模型、编排工具调用、把运行结果回传，直到任务结束。业界常见概括：“除了模型，其余都是 harness。”

所以 **Harness 不包含模型本身**——模型是引擎，harness 是套在外面的那层：给模型的**指令与约束**（系统提示、`AGENTS.md`、change 四件套）、可调用的**工具**（读写文件、执行命令）、以及**循环与边界**（权限限制、结果回传）。Cursor、Codex、Claude Code 都是 harness；同一个模型配不同 harness，行为差异主要来自 harness。

写规约能约束生成，机制就在这里：`AGENTS.md` 与 change 四件套**本身就是 harness 的一部分**，不是给模型的“参考意见”。

#### 哪些交给它，哪些必须由你负责

| 环节 | Harness 负责 | 必须由你负责 |
| --- | --- | --- |
| 范围 | 在给定规约内把功能实现出来 | 范围由 `proposal.md` 与 Non-goals 决定，不随其超出规约的自发改动而扩张 |
| 依据 | 先读 `design.md` 与 delta spec，再动手改代码 | 规约含糊或缺失时先改规约，而不是由它自行裁量 |
| 判定 | 执行命令，给出运行输出 | “是否合格”由 Scenario 与运行结果判定，不由它自己下的结论判定 |
| 责任 | 按你的驳回理由重做 | **提交人对产出负责，审查责任不因使用工具而转移** |

> **记住这一条：**把规约交给 Harness，是为了让它按字面实现。若它额外生成了规约中未声明的功能，问题通常出在规约缺了“不做”的条目——先补规约，再删代码。

### 3. 本课在 OpenSpec 中的位置

**第 2 课把需求写成了 change 的四件套；本课是同一个变更的后三步：实施、校验、归档。**

#### 知识点

#### 一次变更 = 一个 change

OpenSpec 把规约做成仓库里的一等工程制品：`openspec/changes/<change>/` 下的四份 Markdown 就是这次变更的全部依据。流程围绕这四份文件推进，不围绕对话。

一次变更走五步：**提变更**（Propose）→ **评审**（Review）→ **实施**（Apply）→ **校验**（Verify）→ **归档**（Archive）。第 2 课做完前两步，本课做完后三步。

四件套各管一段：`proposal.md` 说为什么做、明确不做什么；`design.md` 说怎么做；`specs/<capability>/spec.md` 用 Requirement 与 Scenario 说「做到什么算合格」；`tasks.md` 把实现拆成一条条带 `verify` 的待办。

#### 本课在五步中的位置

| 步骤 | 做什么 | 产物 | 本课 |
| --- | --- | --- | --- |
| Propose 提变更 | 把需求写进 change，不允许只停留在对话里 | 四件套初稿 | 第 2 课 |
| Review 评审 | 交叉阅读：范围对不对、每条要求能否判定 | 修订后的四件套 | 第 2 课 |
| Apply 实施 | 按 `tasks.md` 逐项实现，完成一项勾一项 | 代码 + 勾选后的 `tasks.md` | **本课做** |
| Verify 校验 | 结构校验 + Scenario 逐条判定 | `validate` 通过、验收证据 | **本课做** |
| Archive 归档 | delta 合并进主力规约，change 移入归档目录 | `openspec/specs/` 更新 | **本课做** |

> **本课的边界：只动 change 目录。**`openspec/specs/` **是长期事实来源（source of truth），只由归档更新**。Apply 期间发现规约要改，改的是 change 里的 delta（`specs/<capability>/spec.md`），不是主力规约——一旦回写主力规约，delta 就失去比对基线，归档时也就无法判断这次究竟改了什么。

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 本人 change 目录是否四件套齐全？ | 齐全：`proposal.md`、`design.md`、`tasks.md`、`specs/<capability>/spec.md`。 | **规约**：`openspec/changes/<change>/` 下四文件齐全（演示仓 change 名 `add-auth-rbac-class-knowledge`：`proposal.md`、`design.md`、`tasks.md`、`specs/auth-upload/spec.md`）<br>**代码**：仓库里 change 目录的实际文件<br>**运行**：`openspec list` 能看到本 change | ☐ |
| 本能力是否还没出现在主力规约里？ | 还没出现。`openspec/specs/` 只由归档更新；若已出现，说明有人提前回写了主规约。 | **规约**：`proposal.md` 的 Modified Capabilities 与 `openspec/specs/` 归档约定<br>**代码**：看 `openspec/specs/` 下的目录<br>**运行**：`openspec list --specs`，本能力应不在其中 | ☐ |
| `tasks.md` 的待办是否仍全部未勾选？ | 第 2 课交付时全部是 `[ ]`；勾选从本课第一项 task 才开始。 | **规约**：`openspec/changes/<change>/tasks.md` 开工前全部为 `[ ]`<br>**代码**：打开 `tasks.md` 看方括号<br>**运行**：统计已勾选项数量，开工前应为 0 | ☐ |

#### 动手要做

- 在学期仓根执行 `openspec list`，确认本 change 在活动列表中。
- 执行 `openspec list --specs`，确认主力规约里还没有本能力——它要等归档之后才出现。
- 打开 `openspec/changes/<change>/`，通读四件套：`proposal.md`（范围与 Non-goals）、`design.md`（决策与接口）、`specs/auth-upload/spec.md`（Requirement / Scenario）、`tasks.md`（顺序与 verify）。讲师规约 / Apply 起点：`AI-DevOps/project-src/week03/`；Apply 完成可运行对照：`AI-DevOps/project-src/week03-applied/`。

### 4. 三个必须记住的判断

全课的知识基础。后面每一步的核对，都在验证这三条是否落进了规约与代码。

#### 知识点

#### 规约是契约，代码是派生物

vibe coding（对话式即兴生成）以对话为准，SDD（Spec-Driven Development，规约驱动开发）以规约为准。本课的驳回、验收与质量门禁（gate）都来自这个区别。**Harness（AI 编码代理）生成的代码若偏离规约，应引用 Scenario（场景）驳回，而不是通过追加对话不断扩大范围。**

#### 认证、授权、隔离是三件不同的事

**认证回答你是谁；授权回答你能做什么；隔离回答你能看见哪一块数据。**缺会话属性（用户、角色、班级）时，后面的需求无法判定。

#### 访问控制必须在服务端强制执行

Saltzer（杰罗姆·萨尔策）与 Schroeder（迈克尔·施罗德）在 1975 年论文《计算机系统中的信息保护》（The Protection of Information in Computer Systems）中提出的安全设计原则：默认拒绝（Fail-Safe Defaults）、最小权限（Least Privilege）、每次请求完整校验（Complete Mediation）。**前端隐藏按钮只降低可发现性，不构成访问控制。**对应威胁：垂直越权（BFLA，Broken Function Level Authorization，学生调用教师专属接口）与水平越权（BOLA / IDOR，Broken Object Level Authorization / Insecure Direct Object Reference，同角色访问其他班级数据）。

### 5. 交付纪律：三条被否决的做法

这三种做法都会让“实现是否可判定”失去依据，因此本课明确否决。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| vibe coding 一次生成 | 对话即需求，速度快，但规约与验收标准难以保持一致。 | 否决。本课用 SDD：**规约是契约，代码是派生物。** |
| 只写规约不发布 | 设计完整但第三方无法启动。 | 否决。本课要用 Compose 交付迭代 1 的成果。 |
| 分组共用仓库 | 协作快，责任不清。 | 否决。个人独立提交，互验用同伴交叉验证。 |

> 把否决理由用自己的话写进 design / 迭代说明。原文照录本表不算 ADR（Architecture Decision Record，架构决策记录）。

### 本课要交付什么

用 Docker Compose 在本机启动一个可登录、可隔离、可上传入库的 CampusClaw 基础版本。这一版只做教研材料与知识库底座，智能备课、智能命题、学情诊断等能力留待后续迭代。验收以本人学期仓库中的 OpenSpec 规约为准；**技术栈若与第 2 课 design 不一致，先改规约再实现。**

- **要做成什么样**：登录权限、隔离、材料与页面体验
- **系统怎么走**：浏览器 → Nginx → Go → MySQL
- **安全与部署**：哈希、Cookie、环境变量、Compose
- **认证方案对照**：会话、JWT、Refresh、OAuth 的取舍
- **实现路线图**：八步，一步一轮，不要一次性生成全站
- **实现方案核对总表**：八步决策点汇总，可打印后逐项勾选

> 请独立完成、独立提交。本教程按当前需求描述编写，不是作业提交系统，也不提供可整体复制仓库的参考实现。

### 想一想：判断与取舍

**先对照本人规约作答。引用不到原文，先改规约再写代码。**

- 本人规约里，未登录访问受保护接口时，是否写明响应不得含材料标题或正文？只写跳转登录页够不够？
- 本课只做迭代 1。本人规约的 Non-goals（明确不做项）是否写清？若没写，Harness 会替你把哪些越界功能“补”进来？
- 若把登录态从服务端会话（session）换成 JWT（JSON Web Token），本课哪几条验收会变成无法判定？为什么？

### 1. 账号与角色：谁能做什么

本迭代只实现教师与学生两种角色的权限；平台超级管理员是产品完整形态里必然存在的角色，但不在本迭代。**能力边界要写成可判定的要求，而不是界面上看不看得见。**

#### 知识点

#### 最小权限

教师可上传、查看、下载；学生只能查看和下载。**多给的能力就是垂直越权面。**角色来自服务端会话，不来自前端切换。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 三角色：管理员 / 教师 / 学生 | 管理员跨班运维方便。 | 本迭代不做，推迟到后续迭代：超级管理员天然跨班，会与“跨班返回 404”的隔离验收直接冲突。隔离验收通过后再单独设计它的越权路径与操作审计。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 角色与能力边界是否逐条写成可判定的要求？ | 教师＝上传/查看/下载；学生＝查看/下载。多给一项能力就多一个垂直越权面。 | **规约**：Requirement 中每个角色各有哪些 Scenario<br>**代码**：搜角色常量与权限判断分支，看学生分支是否出现写操作<br>**运行**：分别用教师与学生账号各试一次上传 | ☐ |

#### 动手要做

- 账号密码登录；角色只有教师与学生。
- 教师可上传、查看、下载本班材料；学生只能查看和下载。
- **身份、角色、班级由服务端会话识别，不信任客户端自行声明。**

### 2. 班级：数据边界从哪里来

每个用户属于固定班级，班级取自服务端会话，不能由请求参数决定。

#### 知识点

#### 班级是租户边界

在同一个数据库实例中用 class_id 划分班级数据边界。用户属于固定班级，不能通过请求参数切换班级。**这是多租户数据隔离，不是前端菜单过滤。**

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 以学校或课程为租户 | 更接近最终产品。 | 本课租户是班级，边界清晰，种子两班即可验收。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 班级边界是写进规约，还是只写在 design 里？ | 必须作为 Requirement 的 Scenario 出现，隔离失败才有判定依据。 | **规约**：跨班访问是否写成可判定的 Scenario<br>**代码**：对比 spec.md 与 design.md 中关于 class 的描述层级<br>**运行**：按 Scenario 逐条跑失败路径，看是否都能判通过与否 | ☐ |

#### 动手要做

- 每个用户属于一个固定班级。
- 只能访问自己班级的材料；跨班由服务端拒绝。

### 3. 材料与知识库：本迭代做到哪一步

材料上传、提取正文、本班可查；知识库本课只负责存正文，不做问答。

#### 知识点

#### 知识库本课只负责存

上传后提取正文写入可查询的数据行，为后续检索预置数据。本班列表搜索可以做；向量检索、问答与 RAG（Retrieval-Augmented Generation，检索增强生成）不是本迭代的范围。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 本课直接做 RAG / 问答 | 演示效果强。 | 否决。没有可靠的入库与隔离，检索会造成跨班数据泄露。本迭代的知识库只负责存储正文。 |
| 列表硬编码演示数据 | 前端实现最快。 | 否决。必须从数据库查询，否则上传与隔离无法验收。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| Non-goals 是否写明检索、问答、作业不做？ | 必须写明。缺失时 Harness 最容易越界生成整块功能。 | **规约**：proposal.md 的 Non-goals（明确不做项）章节<br>**代码**：搜依赖清单与路由，看有无向量库、对话接口<br>**运行**：让 Harness 复述范围，观察是否夹带不做项 | ☐ |
| 列表与搜索的数据来源是否写明？ | 必须来自按班级过滤的数据库查询，不得硬编码演示条目。 | **规约**：列表中是否写明数据来源与过滤条件<br>**代码**：搜列表 handler，看查询语句是否带 class_id<br>**运行**：清空材料表后刷新列表，应无任何条目 | ☐ |
| 上传校验与失败状态是否可判定？ | 扩展名、大小、内容三类失败各有明确状态码，且数据库与磁盘无残留。 | **规约**：是否有对应 Scenario 与预期状态码<br>**代码**：搜校验分支与错误返回位置<br>**运行**：分别上传 .exe、超限文件、非法编码文件各一次 | ☐ |

#### 动手要做

**规约必做（演示 change：`specs/auth-upload/spec.md` R4–R5、R9、R10）：**

- 教师上传 `.txt` / `.md`；解析正文并在同事务内写入 `materials` 与 `knowledge_entries`（R4）。
- 本班列表由数据库按会话班级过滤；详情与文件经鉴权 API（R3、R5、R9.4），不得静态暴露 `/uploads`。
- 上传须校验扩展名与大小上限；解析/入库失败时两表与磁盘均无残留（R4.4–R4.7）。
- Web：登录页 + 材料页；`/api/me`、401 回登录、正文安全（R9）；北大红品牌、深浅色、列表/网格、本班搜索、命令面板、上传进度、toast、Markdown GFM（R10）。

### 1. 请求链路：浏览器 → Nginx → Go → MySQL

只有一条链路，信任边界落在 Go；浏览器与静态页一律不可信。

#### 知识点

#### 信任边界在 API

**浏览器与静态页不可信。认证、授权、隔离、上传校验全部发生在 Go。**Nginx 只托管前端静态资源，并将 /api 反向代理到 Go 后端，不得将上传目录作为静态资源目录暴露。

#### 同源与反向代理

前端通过同源 /api 调用后端，避免跨域请求带来的 Cookie 作用域与 SameSite 策略问题。开发时 Vite 的代理路径应与生产环境 Nginx 保持一致。

> 请求链路：浏览器只与 web 通信；认证、授权、隔离与上传校验全部发生在信任边界之后（Go）。
> 图中标注：docker compose 内部网络 / 浏览器 / 前端 SPA（不可信） / 唯一暴露端口 :8080 / web · Nginx / 静态资源 + 反代 /api / 反代 /api / 信任边界：进入 Go 后全部校验 / api · Go / 认证 · 授权 · 隔离 / 上传校验 / 普通账号 / db · MySQL / 不映射宿主端口 / 上传目录 / 仅挂载到 api / 数据卷 volume / down 后数据仍在

### 1. 凭据怎么存：哈希与环境变量

口令只以加盐慢哈希入库，所有密钥来自环境变量；缺失就启动失败，不留内置默认值。

#### 知识点

#### 口令与会话密钥

明文口令一旦入库即失去意义。用加盐慢哈希（bcrypt，一种专门用于口令的慢哈希算法）增加离线破解成本。SESSION_SECRET 用于保护会话标识，缺失必须启动失败，禁止内置默认值。**密钥进 Git 是发布阻断项，泄漏后要轮换而不是只删提交。**

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| argon2 替代 bcrypt | 同为加盐慢哈希，argon2 更抗 GPU 并行破解。 | 可。本课用 bcrypt，Go 官方扩展库即可实现；不要存明文或可逆加密。 |
| 密钥写进源码默认值 | 本地环境始终可用。 | 否决。缺失必须启动失败。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 口令是以哈希形式保存的吗？ | bcrypt 加盐慢哈希；不存明文，也不用可逆加密。 | **规约**：`specs/auth-upload/spec.md` R7（密码哈希与会话密钥）<br>**代码**：搜明文赋值与哈希调用位置<br>**运行**：直接查 users 表，看口令字段形态 | ☐ |
| 会话密钥与数据库口令来自环境变量吗？ | 只来自环境变量；缺失则启动失败，无内置默认值。 | **规约**：`specs/auth-upload/spec.md` R7.3 / R7.5 与 `design.md`「配置与启动」<br>**代码**：搜默认值常量与 os.Getenv / process.env 读取点<br>**运行**：删掉 .env 后启动，应失败而非照常启动 | ☐ |

- 口令用 bcrypt 哈希保存，不存明文。
- 登录状态用 `HttpOnly`、`SameSite=Lax` Cookie 维护。
- 口令、数据库凭据、会话密钥走环境变量；缺失则启动失败，不要内置默认值。

### 2. 失败响应同形：不给账号枚举留依据

未登录、越权、口令错误对外必须给出无法区分的响应，排障信息只进服务端日志。

#### 知识点

#### 默认拒绝与完整校验

未登录默认 401；未知角色不能升权。每次请求都要从会话再读角色与班级，**不能信任上一次缓存在浏览器里的声明。**

#### 信息隐藏

错误提示、限流响应、跨班响应都可能成为账号枚举的依据。**对外统一失败响应，排障信息只记录在服务端日志。**

> 图：失败响应同形。差异化文案、限流 429、异常耗时都会成为枚举依据；真实原因只进服务端日志。
> 图中标注：账号不存在 / 口令错误 / 触发限流 / 对外：同一响应 / 相同状态码 · 相同文案 / 相近耗时 / 三种原因不可区分 / 攻击者视角 / 得不到任何区分依据 / → 账号枚举不可行 / 服务端日志 / 记录真实原因，仅供排障

| 会话 + HttpOnly Cookie | 服务端会话表；客户端只有不透明 ID | 删会话行，立刻失效 | 同源 Web | 要做 |
| 会话 ID 放 Authorization 头 | 仍是服务端会话 | 同样立刻失效 | SPA 跨域、移动端 | 了解 |
| JWT access token | 载荷在客户端；服务端验签名 | 过期前难作废 | 无状态 API、多实例 | 了解，不做 |
| Access + Refresh | 短 token + 可轮转的长 token | 吊销 refresh | 移动端、开放 API | 了解，不做 |
| OAuth / OIDC / SSO | 外部 IdP 发令牌 | 跟 IdP 会话有关 | 校园统一身份 | 了解，不做 |
| API Key | 长期密钥 | 轮换密钥 | 机器对机器 | 了解，不做 |

#### 知识点

#### JWT（JSON Web Token）

由三段组成：头部（Header）、载荷（Payload）、签名（Signature）。载荷可携带 user_id、role、exp 等声明。校验签名即可承认身份，服务端不必每请求查会话表，利于无状态水平扩展。代价：载荷默认可见（Base64 编码不是加密）；将 role 写入 token 后，修改角色需等 token 过期；登出不能立刻作废，除非额外维护黑名单，相当于又把状态管理引回服务端。

#### Access token 与 Refresh token

短期 access token 用于调用 API，长期 refresh token 用于换取新的 access token。降低令牌泄露后的可用窗口，并可通过 refresh 轮转检测盗用。实现复杂度高：存储、轮转、重放、吊销。本课单实例浏览器应用不需要这套。

#### OAuth 2.0 / OIDC / SSO

把登录委托给学校的 IdP（Identity Provider，身份提供方）或 GitHub 等。OAuth 2.0 负责授权，OIDC（OpenID Connect）在其之上增加身份认证层。适合多系统共用校园账号。本课要练习的是自己系统内的会话管理、RBAC（Role-Based Access Control，基于角色的访问控制）与班级边界，不接入外部身份。

#### API Key

给机器调用的长期密钥，通常放在请求头。没有浏览器会话、没有登录页。适合脚本与对内服务，不适合教师与学生交互，也难以按用户吊销，无法支撑班级隔离。

### 2. 本课的选择：服务端会话 Cookie

**同源浏览器站点、登出可立刻失效、角色与班级不放进客户端载荷——这三条决定了本课的技术选型。**

#### 知识点

#### 不透明会话 ID

服务端保存会话行，客户端只持有随机 ID。登出删除会话行即失效；角色与班级每次从数据库读取。传输可以走 Cookie（本课），也可以走 Authorization 头，后者需要前端自行存储并附带，容易落入 localStorage。

#### Cookie 与 CSRF / XSS

Cookie 会被浏览器在同站请求里自动带上，要防跨站伪造（CSRF）：同源、SameSite、必要时 CSRF token。JWT 放请求头不会自动跨站带出，CSRF 风险面小，但若存入 localStorage，一旦出现 XSS（跨站脚本）漏洞即可被读走。这是一个典型的权衡（trade-off）：**Cookie 方案主要面临 CSRF 风险，客户端存储 token 主要面临 XSS 风险。**

> 两种登录态的本质差异是「状态放在哪里」：它决定登出语义、改角色的生效时间与主要防范的风险类型。
> 图中标注：服务端会话 Cookie（本课采用） / 浏览器 Cookie / 只持有随机 ID / 服务端会话表 / user · role · class / 状态在服务端 / 登出 = 删除会话行，立刻失效 / 主要风险：CSRF → 同源 + SameSite / 角色与班级每次从数据库读取 / JWT（本课不采用） / token（三段） / role 写在载荷里 / 服务端只验签 / 不查会话表 / 状态在客户端，载荷默认可见 / 登出 ≠ 立刻失效（需另维护黑名单） / 主要风险：XSS 读走 localStorage / 改角色要等 token 过期才生效

#### 本课为何选会话 Cookie

- 前后端同源，Nginx 反向代理 `/api`，Cookie 自动带上，前端无需自行保管 token。
- 班级隔离要求每次以服务端身份为准；JWT 载荷中的 class_id 容易诱使实现去信任客户端数据。
- 验收包含登出后 401；会话删行即可判定，JWT 还要额外讲黑名单。
- 当前单实例。多副本与无状态 JWT 的取舍放到后续部署课，不要提前换方案。

## 3 登录与会话

登录成功后建立服务端会话（session）。**会话中缺失的属性，服务端后续无法补齐，相关需求即不可判定。**

> 每步按同一顺序展开：**知识点** → **其他可行方案与选择依据** → **本步要核对** → **动手要做**。“怎么查”一列给出三处证据：规约读哪条、代码搜什么、运行做什么；发现不一致，先补规约或改实现。全课汇总见 实现方案核对总表。

### 1. 会话要承载什么，放在哪里

认证只回答“你是谁”；**会话要能判定 user_id、role、class_id，而这三项不交给客户端保管。**

#### 知识点

#### 认证不是授权

认证证明你是某个账号。授权决定教师能否上传、学生能否只读。先认证再授权。会话至少能判定 user_id、role、class_id。

#### 服务端会话与 Cookie 属性

会话 ID 是不透明随机串，放在 HttpOnly Cookie 里。浏览器自动带上，脚本读不到。SameSite=Lax 限制跨站带 Cookie。角色与班级每次从用户表读取，不采信客户端回传。

| SameSite=None; Secure | 跨站嵌入需要。 | 本课同源，Lax 足够。本机 HTTP 环境不要强制设置 Secure 属性，否则浏览器会拒绝写入 Cookie。 |

### 2. 登录、登出与会话固定

登录换发新 ID、登出删服务端会话行——这两件事决定登录态能否立刻失效。

#### 知识点

#### 会话固定

**登录成功必须签发新 ID，并作废登录前的会话。**否则攻击者可诱使受害者使用已知的会话 ID，待其登录后共用同一会话。

> 会话固定（session fixation）的防御：登录成功必须换发新会话 ID，攻击者预置的旧 ID 随之作废。
> 图中标注：攻击者 / 受害者浏览器 / 服务端 / ① 正常登录，获得会话 ID = A / ② 诱使受害者携带 ID = A 访问 / ③ 携带 ID = A 提交登录 / ④ 校验通过 → 签发新 ID = B / 旧 ID = A 即刻作废 / ⑤ Set-Cookie：ID = B / ⑥ 攻击者持旧 ID = A 请求 → 401

#### 默认拒绝

仅重定向到登录页不够。**受保护 API 必须 401，且响应体不得含标题、正文、路径。**

### 3. 防枚举、限流与方案边界

用户不存在与口令错误必须无法区分；同时明确本迭代不引入 JWT。

#### 知识点

#### 账号枚举与限流

用户不存在与口令错误若返回不同文案或耗时，可被用来探测账号。**统一提示文案，并对用户名 + IP 组合做限流。**锁定期的响应仍与凭据错误一致，避免 429 本身成为账号枚举的依据。

#### 为什么不用 JWT / Bearer token

本迭代是浏览器同源站点，不是开放 API 或移动端。JWT 常被存入 localStorage，脚本可读，一旦出现 XSS（跨站脚本）漏洞即被窃取；载荷里的 role / class_id 容易被当成授权依据。登出时服务端删会话行即可立刻失效；无状态 JWT 在过期前很难作废，还要引入黑名单，等于又回到服务端会话模式。OAuth / SSO（单点登录）属于联邦身份（Federated Identity）体系，超出本课范围。Cookie 里的会话 ID 也是一种 token，只是不把权限声明交给客户端保管。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| JWT / Refresh / OAuth | 见认证方案对照页。 | 了解机制与代价。本课选会话 Cookie：同源、可立刻登出、班级信息不放入客户端载荷。 |
| Redis 存会话与限流 | 多副本共享状态。 | 本课单实例、会话在 MySQL 即可。多副本再引入共享存储。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 失败提示与耗时是否统一？ | 账号不存在与口令错误返回一致，并做等价耗时的哈希比较。 | **规约**：是否写明统一失败响应<br>**代码**：搜错误分支与哈希比较的位置<br>**运行**：两种输入各试一次，比状态码、响应体与耗时 | ☐ |

#### 动手要做

- 失败提示统一，不区分用户不存在与口令错误。用户不存在时也做一次等价耗时的哈希比较。
- 对用户名 + IP 做失败限流；锁定期内即使口令正确也拒绝，响应仍与凭据错误一致。
- 不要签发 JWT，也不要把会话 ID 或角色写进 `localStorage`。其他方案见 认证方案对照，本课只实现会话 Cookie。
- `GET /api/me` 返回当前角色与班级，供前端决定是否渲染上传入口。

## 4 班级隔离

#### BOLA / IDOR

### 3. 跨班返回 403 还是 404

#### 403 与 404

## 5 上传入库

教师上传后写入磁盘、解析正文，并在同一事务中写入材料表与知识库表。

### 1. 权限：谁可以上传

上传是教师专属功能；仅隐藏按钮无效，必须以会话角色在服务端拒绝。

#### 知识点

#### BFLA 垂直越权

Broken Function Level Authorization：学生调用只有教师可用的上传接口。**仅隐藏前端按钮不能阻止越权。必须以会话角色在服务端拒绝，数据库与磁盘状态均不变。**

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 学生调用上传接口的结果是什么？ | 403，且材料表、知识库表行数与上传目录均不变。 | **规约**：学生上传失败 Scenario<br>**代码**：搜上传 handler 的角色判断位置<br>**运行**：用学生 Cookie 调一次上传接口 | ☐ |

#### 动手要做

### 2. 校验与写入磁盘

白名单扩展名、服务端生成存储名、超限在读完整请求体之前拒绝。

#### 知识点

#### 白名单与路径穿越

只允许 .txt / .md。**黑名单机制无法穷举所有危险类型，必须采用白名单。****客户端文件名可含 ../，存储名必须服务端生成。**上传目录不做静态暴露，读文件先鉴权。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 先写入磁盘再等人审再入库 | 内容安全更严。 | 超出范围。本课校验扩展名、大小、UTF-8 后直接入库。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 扩展名校验是白名单还是黑名单？ | 白名单 .txt / .md；黑名单无法穷举。 | **规约**：是否写明白名单<br>**代码**：搜扩展名允许列表<br>**运行**：分别上传 .exe、.md.exe 各一次 | ☐ |
| 存储名由谁生成？ | 服务端生成；客户端文件名只作展示标题，不参与路径构造。 | **规约**：是否有路径穿越防护要求<br>**代码**：搜文件路径拼接位置<br>**运行**：上传文件名含 ../ 的文件，看文件实际写入路径 | ☐ |

#### 动手要做

- 白名单 `.txt` / `.md`；其他扩展名 400，不留文件。
- 大小上限走环境变量（如 `MAX_UPLOAD_BYTES`）；超限返回 413，应在读取完整请求体之前拒绝。
- 内容必须是非空 UTF-8 文本，否则 400。
- 存储名由服务端生成；客户端文件名只作展示标题，不得参与构造路径。

### 3. 入库事务与下载鉴权

材料行与知识库行同事务，失败不留孤儿；下载走鉴权接口，不暴露静态路径。

#### 知识点

#### 上传是事务

**材料行与知识库行必须处于同一事务。**只写入磁盘而不入库，第 4 课检索将没有数据；只入库而不写入磁盘，下载将无法完成。**失败时要回滚并删除已写入的文件，不得残留孤儿文件或孤儿记录（orphan）。**

> 上传是一次事务：磁盘写入与两表写入同生共死；任何一步失败都回到「无文件、无记录」的干净状态。
> 图中标注：接收 multipart / 教师角色 / 白名单校验 / .txt / .md · 大小上限 / 生成存储名 / 写入上传目录 / 事务写入两表 / materials + knowledge / 校验失败 → 4xx / 不产生文件与记录 / 任一步失败：回滚两表 / 并删除已写入文件 → 无残留 / 提交 → 201 / 两表与文件一致 / 孤儿文件与孤儿记录（orphan）都不允许存在；清理策略须写入规约才可验收

#### 知识库在本课的目的

预置可查询正文，不是做问答。解析失败与非法扩展名都应 4xx，且两表与目录无残留。清理策略写进规约才能验收。

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 对象存储服务（AWS S3 / 阿里云 OSS） | 文件存储与 api 本地磁盘解耦，利于多副本部署。 | 本课单实例本地目录即可。多副本再迁移到对象存储。 |
| 消息队列异步入库 | 上传接口可立即返回，解析失败可重试。 | 代价过高。本课采用同步写入磁盘并在同一事务中入库，失败路径更易验证。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 两张表是否处于同一事务？ | 同事务，任一步失败整体回滚。 | **规约**：是否写明事务要求<br>**代码**：看事务开启与提交的范围<br>**运行**：人为制造一次写入失败，检查是否半提交 | ☐ |

| 下载是否走鉴权接口？ | 走 /api/materials/{id}/file，先校验会话与班级，跨班 404。 | **规约**：是否写明下载鉴权要求<br>**代码**：搜静态目录暴露与文件 handler<br>**运行**：直接猜测 /uploads/<文件名> 请求一次 | ☐ |

### 2. 网络暴露与持久化

#### 校验分两层：结构校验与行为校验

#### 架构决策记录（ADR，Architecture Decision Record）

## 按规约实现

第一次按 SDD（Spec-Driven Development，规约驱动开发）流程做实现。最大风险不是技术，而是跳过规约一次性生成全部代码。

> 每步按同一顺序展开：**知识点** → **其他可行方案与选择依据** → **本步要核对** → **动手要做**。“怎么查”一列给出三处证据：规约读哪条、代码搜什么、运行做什么；发现不一致，先补规约或改实现。全课汇总见 实现方案核对总表。

### 1. Apply 循环：一个 task 一轮

读 task → 实现 → 审查 diff → 运行 verify → 提交；失败不带入下一项。

#### 知识点

#### Apply 循环

读 task → 实现该项 → 对照 spec 审查 diff → 运行 verify → 通过才提交。**一个 task 一次提交，失败项不得带入下一项。**

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 一个提示词生成全仓 | 表面上实现快。 | 否决。按 task 循环，才能审查 diff、运行 verify、必要时回退。 |
| 沿用第 2 课 Propose 对话继续写代码 | 有上下文。 | 否决。对话记忆会取代规约。必须新开会话并先复述范围。 |
| 复制他人学期仓库后修改界面 | 可直接运行。 | 否决。实现必须落在本人 OpenSpec。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 是否一个 task 一轮提交？ | 是：实现 → 审查 diff → 运行 verify → 提交。 | **规约**：`proposal.md` Non-goals 与 `tasks.md` 开头 Apply 约定<br>**代码**：看提交历史粒度<br>**运行**：任取一轮提交，检查是否只对应一个 task | ☐ |

#### Apply 阶段只产生两类改动

一类是**代码**：Harness 依据 delta spec 与 `design.md` 生成，逐 task 审查 diff。另一类是 `tasks.md` 的**勾选**：verify 通过后由人勾上。

除这两类之外，只有一种例外：发现规约本身含糊或缺失。此时先改规约（走 delta，见本页第 2 节），再回到实现——**不允许以代码去迁就规约中含糊的描述。**

#### 动手要做

- 命令：`/opsx-apply`（技能 `openspec-apply-change`）。
- 不要接着第 2 课 Propose 的旧对话生成代码。
- 不要把他人仓库整体复制为作业提交。需求描述说明的是产品范围，实现须落在本人学期仓库。

> **开始 Apply 之前先过准入检查。**以下四条必须能在本人 change 的 delta 里找到原文，缺一条就先补规约再动手：未登录响应不得含材料标题与正文；跨班按 ID 访问已选定 403 或 404 并准备写进 README；租户标识只取自会话、客户端传入一律忽略；上传失败要求库与磁盘均无残留。

### 2. 规约要改，走 delta

**Apply 期间唯一允许改规约的入口是 change 里的 delta，不是主力规约。**

#### 知识点

#### delta 是相对主力规约的差量

change 里的 `specs/<capability>/spec.md` 不是一份完整规约，而是这次变更相对主力规约的**差量**（delta）：只写增了什么、改了什么、删了什么。这样做的好处是归档时能逐条比对，明确知道这次动过哪些要求。

因此 Apply 期间要改规约，改的是 delta。直接编辑 `openspec/specs/` 会把「差量」与「基线」混在一起，归档时无从比对。

#### delta 的分节写法

| 分节标题 | 什么时候用 | 本 change 实例 |
| --- | --- | --- |
| `## ADDED Requirements` | 本次新增的能力 | 本 change 的全部 Requirement 都是新增，所以只有这一节 |
| `## MODIFIED Requirements` | 主力规约里已有、本次要改的要求 | 本课没有——迭代 1 是第一次入库，主力规约还是空的 |
| `## REMOVED Requirements` | 本次要撤掉的要求 | 同上 |
| `## RENAMED Requirements` | 要求改名（较少用） | 同上 |

> 每条 Requirement 写在 `### Requirement: 名称` 下，正文用 MUST / MUST NOT 这类规范性动词；每条 Scenario 写在 `#### Scenario: 名称` 下，用 **WHEN / THEN / AND** 逐行给出可判定的步骤。唯一标准是：仅凭这条 Scenario，能否判定通过或不通过。

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 改规约时改的是 delta，还是主力规约？ | 只改 change 里的 delta。`openspec/specs/` 归归档维护。 | **规约**：只改 `openspec/changes/<change>/specs/` delta，勿写 `openspec/specs/`<br>**代码**：`git status` 看本轮改动的路径<br>**运行**：`openspec list --specs`，归档前不应出现本能力 | ☐ |
| 规约改动是否早于对应代码？ | 是。**先改规约再改代码，否则验收标准会随实现发生偏移。** | **规约**：是否有该流程要求<br>**代码**：看提交顺序<br>**运行**：比较 delta 提交时间与代码提交时间 | ☐ |
| 改完规约是否先校验再继续？ | 是：先 `openspec validate <change> --strict`，确认格式与 Scenario 仍可判定。 | **规约**：是否有该流程要求<br>**代码**：看本轮提交里是否含规约改动<br>**运行**：改完立即跑一次 validate | ☐ |

#### 动手要做

- 规约含糊或缺失时，用 `/opsx-update`（技能 `openspec-update-change`）修改 change 的 delta，不要直接编辑 `openspec/specs/`。

- 改完先跑一次 `openspec validate <change> --strict`，再回到 Apply 循环继续实现。

### 4. Archive：把 delta 合并成基线

**归档对应 OpenSpec 的第五步：change 移入归档目录，delta 并入主力规约，成为下一次迭代的起点。**

#### 知识点

#### 归档把「这次改了什么」并入基线

归档做两件事：把 change 目录移入 `openspec/changes/archive/`，目录名前加归档日期；再把 delta 与主力规约逐条比对，合并进 `openspec/specs/<capability>/spec.md`。

合并之后，主力规约里才第一次出现本能力的要求。此后的迭代从这份 `specs/` 出发——第 4 课的检索增量会在它之上开新 change，而不是从散落的代码或对话里重新生长。

所以归档不是形式动作：不归档，`openspec/specs/` 永远是空的，下一次变更就没有可继承的基线。

#### 归档前后对照

| 位置 | 归档前 | 归档后 |
| --- | --- | --- |
| `openspec/changes/<change>/` | 四件套在此，是活动变更 | 已移走，活动变更清零 |
| `openspec/changes/archive/` | 只有占位文件 | 出现 `YYYY-MM-DD-<change>/`，内含原来的四件套 |
| `openspec/specs/<capability>/spec.md` | 不存在（主力规约还是空的） | 已生成，含本能力的 Requirement 与 Scenario |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 活动变更是否已清零？ | 是：`openspec list` 里不再出现本 change。 | **规约**：是否写明归档要求<br>**代码**：看 `changes/` 与 `changes/archive/`<br>**运行**：`openspec list` | ☐ |
| 主力规约里是否已出现本能力？ | 已出现，且内容与 delta 一致（无遗漏、无多余）。 | **规约**：delta 全文<br>**代码**：`openspec/specs/` 下的规约文件<br>**运行**：`openspec list --specs` 后逐条比对 | ☐ |
| 归档时是否还有未勾选的 task？ | 应无。归档前若有未勾选项会先告警；确认「已完成但漏勾」还是「确实没做」。 | **规约**：`tasks.md` 勾选纪律<br>**代码**：看归档目录里 `tasks.md` 的方括号<br>**运行**：归档前先核对未勾选项数量 | ☐ |

#### 动手要做

- 用 `/opsx-archive`（技能 `openspec-archive-change`）归档，命令等价于 `openspec archive`。
- 归档过程中它会先检查四件套完成度与未勾选项，再比对 delta 与主力规约，让你确认是否先同步规约——选择先同步，再执行归档。
- 归档完成后核对三件事：活动变更清零、`changes/archive/` 出现带日期的目录、`openspec/specs/<capability>/spec.md` 已生成。

> 发布（本迭代的完成定义）是本课流程的最后一环，归档是规约库的收尾动作。当堂能做完最好；发布窗口内来不及的，课后补齐即可——但不要把它当成可选项：不归档，第 4 课就没有可继承的规约基线。

> 把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。

### 1. 为什么必须写 Non-goals

**不写不做项，实现最容易在边界缺失处膨胀；越界功能往往能追溯到规约没有写“不做”。**

#### 知识点

#### 范围蔓延

Harness（AI 编码代理）最容易在 Non-goals（明确不做项）缺失时额外生成聊天界面、JWT、RAG。**把不做项写进规约，为 Apply 阶段提供了硬性约束。**

#### 其他可行方案与选择依据

| 方案 | 要点 | 本课如何取舍 |
| --- | --- | --- |
| 本课做 RAG / 对话助手 | 产品形态看起来更完整。 | 否决。**隔离与入库尚未稳定时，问答会造成跨班数据泄露。**第 4 课再扩展检索。 |
| 本课接校园 SSO（Single Sign-On，单点登录） | 账号登录体验统一。 | 否决。应先掌握自己签发会话、登出与 RBAC 的实现。方案对照见认证方案页。 |
| 本课上 K8s（Kubernetes，容器编排平台）多副本 | 更接近生产环境。 | 否决。进程内限流与会话在多副本下会出错。标准启动是单实例 Compose。 |

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 本人 Non-goals 是否写明检索、问答、作业不做？ | 写明。缺失时 Harness 最容易越界生成。 | **规约**：proposal.md 的 Non-goals 章节<br>**代码**：对照规约与代码，看有无未声明功能<br>**运行**：让 Harness 复述不做项，看是否一致 | ☐ |

### 2. 越界实现的识别与自查

知识库只存可查正文；**发现越界功能时先补规约，而不是先改文档迁就代码。**

#### 知识点

#### 知识库不等于问答

本课只存可查正文。列表快捷搜索可以做。向量化、RAG、作业流程会改变数据模型和验收，不要提前做。

#### JWT 不是本课认证方案

当前需求写明服务端 Session Cookie。把 Bearer token 写进前端再当授权依据，属于范围蔓延，也把租户标识交回客户端。

> **Non-goals 属于 `proposal.md`。**发现越界实现时，先用 `/opsx-update`（技能 `openspec-update-change`）把不做项与边界补进 change 的 `proposal.md` 与 delta，再删代码。只删代码不改规约，下一次生成还会把它补回来。

#### 本步要核对

| 核对项 | 本迭代应采用 | 怎么查（规约 / 代码 / 运行） | 自检 |
| --- | --- | --- | --- |
| 代码里是否出现越界实现？ | 无 JWT / OAuth、无向量库、无对话接口。 | **规约**：不做项清单<br>**代码**：搜依赖清单、路由与前端页面<br>**运行**：逐个访问新增页面，确认是否属于本迭代范围 | ☐ |
| 知识库是否只存可查正文？ | 是，未提前向量化，为下一迭代预留。 | **规约**：知识库在本迭代的定位<br>**代码**：看 knowledge_entries 表结构<br>**运行**：查库确认只有正文类字段，无向量列 | ☐ |

### 3. 本迭代不做的清单

清单要落到本人规约的 Non-goals 一节，提交前逐条自查。

#### 本迭代必须验收的 Web（spec R9 + R10）

- 行为与安全：两页、`GET /api/me`、鉴权 API、401 回登录、防脚本（R9）。
- 视觉与交互：北大红、深浅色、响应式、列表/网格、本班搜索、⌘/Ctrl+K 命令面板、上传进度、toast、Markdown GFM（R10）。

#### 动手要做：Non-goals 写入本人 proposal

- 知识库问答、向量检索、RAG。本课知识库只存可查正文。
- 对话助手、作业布置与批改、成绩与错题本。
- JWT / OAuth / SSO。登录态用服务端会话 Cookie，不要用 localStorage 里的 Bearer token。
- 注册改密、多校多租户、验证码或邮箱短信登录。
- PDF / Word / 图片解析，以及在线预览与编辑。
- Kubernetes、CI、公网域名、HTTPS 证书、多副本高可用。当前单实例 Compose。

> 页面再完整，也不能代替服务端鉴权。用 `curl` 仍能绕过班级隔离或让学生上传成功，本课不算完成。

#### 为什么本迭代不做平台超级管理员

> **产品完整形态里一定会有这个角色**（跨班运维、账号与班级管理），但它在任何一次迭代里都应当是**单独设计**的一项，而不是顺带做出来的：

- **它与本迭代的隔离验收直接冲突。**超级管理员天然跨班，而本迭代把“跨班访问与记录不存在返回同一个 404”作为隔离成立的证据。先放进一个可以合法跨班的角色，那个 404 就不再能作为证据。
- **它的风险点与教师/学生完全不同。**教师与学生之间的越权是“同角色、不同班级”；超级管理员是**系统内唯一允许跨班的角色**，需要的是操作审计、二次确认与最小化授权，属于另一组规约。
- **所以正确顺序是：先让隔离可判定并验收通过，再单独开一次变更引入它。**表结构可以预留字段，但本迭代不验收、不实现入口。

> **本迭代要做的只有一件事：把它写进 `proposal.md` 的 Non-goals。**不写，Harness 很可能在未声明的情况下生成一个管理员入口或一条可跨班的查询分支——即便界面上看不见，它也已经绕过了隔离。

> **可直接写入本人 Non-goals 的表述（可按自己的话改写）：**
> `- 平台超级管理员：产品完整形态里必然存在的角色，本迭代不做。它跨班可见，会与班级隔离的验收冲突；留待隔离稳定后单独开一次变更，设计其越权路径与操作审计。`

> 把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。
