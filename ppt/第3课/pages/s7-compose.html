1一套命令启动可复现的环境

发布形态是 Compose，不是本机脚本。

知识点

环境等价

Compose 把 web、api、db 固定为一套可复现的环境。本机直接运行 Go 程序能够通过、别人按 README 无法启动，就不算发布。

方案 要点 本课如何取舍
本机直接跑二进制 + 云数据库 开发便捷。 不能当作发布形态。标准启动必须是 Compose。

2网络暴露与持久化

只有 web 映射宿主端口；数据落在 volume，down 之后再 up（不加 -v）数据应当还在。

知识点

内部网络

db 不映射宿主端口，减少误暴露。api 使用普通账号连接数据库，管理员口令不下发。上传目录只挂载到 api。

持久化

volume 保存数据库与文件。down 之后再 up（不加 -v），数据应当仍然存在。-v 会清空数据卷，只用于主动重置数据。

其他可行方案与选择依据

方案 要点 本课如何取舍
把 3306 映射出来方便调试 便于用图形化客户端连接数据库。 默认否决。确需时通过 compose exec 进入 mysql 容器执行。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
是否只有 web 映射宿主端口？ db 不映射；api 不单独暴露。 规约：攻击面最小化要求
代码：看三个服务的 ports 配置
运行：扫描本机监听端口，确认只有 web 端口
down 之后 up，数据是否仍在？ 在（不加 -v）；-v 仅用于主动重置。 规约：是否写明持久化要求
代码：看 volume 配置与挂载点
运行：执行 down 与 up 一轮后查询数据

动手要做

  • 上传目录挂载到 api；数据库使用 volume，并按持久化要求执行一轮 down / up 验证。
  • 应用以普通数据库账号连接数据库，不要使用管理员账号；管理员口令不要写入 .env 下发给 api。

3就绪等待与单实例边界

depends_on 只保证启动顺序，不保证数据库可连；进程内的会话与限流决定了本迭代只能单实例。

知识点

depends_on 不等于就绪

容器状态为 started，不代表 MySQL 已经可连接。应用要重试等待数据库。首次访问返回 502 通常是数据库仍在初始化。

单实例

进程内限流、本地会话计数在多副本下会失效。本迭代明确单实例，多副本留到后续课。

其他可行方案与选择依据

方案 要点 本课如何取舍
Kubernetes / 多副本 生产环境常见。 本课不做。限流与会话若存放在进程内存，多副本下会出错。
healthcheck 失败即重启 api 自愈。 不要把数据库探活并入存活探针（liveness），否则数据库抖动会触发重启并放大故障。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
除 depends_on 外是否有就绪重试？ 应用重试等待数据库可连接，避免首次启动失败。 规约：是否写明就绪等待要求
代码：看启动时的数据库连接逻辑
运行：全新启动一次，观察是否出现 502
限流与会话是否只存在进程内存？ 是，因此必须声明单实例；多副本下状态会不一致。 规约：是否写明单实例部署
代码：搜限流器与会话存储的位置
运行：启动两个 api 副本，观察限流与会话状态是否不一致

动手要做

  • GET /health 无需登录，只做存活判定，不要和数据库探活混成同一个语义。

首次启动 MySQL 可能需要几十秒，期间入口可能短暂返回 502。端口被占用时用 WEB_PORT 修改。

把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。
