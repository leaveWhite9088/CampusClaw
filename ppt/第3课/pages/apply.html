按规约实现

第一次按 SDD（Spec-Driven Development，规约驱动开发）流程做实现。最大风险不是技术，而是跳过规约一次性生成全部代码。

每步按同一顺序展开：知识点 → 其他可行方案与选择依据 → 本步要核对 → 动手要做。“怎么查”一列给出三处证据：规约读哪条、代码搜什么、运行做什么；发现不一致，先补规约或改实现。全课汇总见 实现方案核对总表。

1Apply 循环：一个 task 一轮

读 task → 实现 → 审查 diff → 运行 verify → 提交；失败不带入下一项。

知识点

Apply 循环

读 task → 实现该项 → 对照 spec 审查 diff → 运行 verify → 通过才提交。一个 task 一次提交，失败项不得带入下一项。

其他可行方案与选择依据

方案 要点 本课如何取舍
一个提示词生成全仓 表面上实现快。 否决。按 task 循环，才能审查 diff、运行 verify、必要时回退。
沿用第 2 课 Propose 对话继续写代码 有上下文。 否决。对话记忆会取代规约。必须新开会话并先复述范围。
复制他人学期仓库后修改界面 可直接运行。 否决。实现必须落在本人 OpenSpec。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
是否一个 task 一轮提交？ 是：实现 → 审查 diff → 运行 verify → 提交。 规约：proposal.md Non-goals 与 tasks.md 开头 Apply 约定
代码：看提交历史粒度
运行：任取一轮提交，检查是否只对应一个 task

Apply 阶段只产生两类改动

一类是代码：Harness 依据 delta spec 与 design.md 生成，逐 task 审查 diff。另一类是 tasks.md 的勾选：verify 通过后由人勾上。

除这两类之外，只有一种例外：发现规约本身含糊或缺失。此时先改规约（走 delta，见本页第 2 节），再回到实现——不允许以代码去迁就规约中含糊的描述。

动手要做

  • 命令：/opsx-apply（技能 openspec-apply-change）。
  • 不要接着第 2 课 Propose 的旧对话生成代码。
  • 不要把他人仓库整体复制为作业提交。需求描述说明的是产品范围，实现须落在本人学期仓库。
开始 Apply 之前先过准入检查。以下四条必须能在本人 change 的 delta 里找到原文，缺一条就先补规约再动手：未登录响应不得含材料标题与正文；跨班按 ID 访问已选定 403 或 404 并准备写进 README；租户标识只取自会话、客户端传入一律忽略；上传失败要求库与磁盘均无残留。

2规约要改，走 delta

Apply 期间唯一允许改规约的入口是 change 里的 delta，不是主力规约。

知识点

delta 是相对主力规约的差量

change 里的 specs/<capability>/spec.md 不是一份完整规约，而是这次变更相对主力规约的差量（delta）：只写增了什么、改了什么、删了什么。这样做的好处是归档时能逐条比对，明确知道这次动过哪些要求。

因此 Apply 期间要改规约，改的是 delta。直接编辑 openspec/specs/ 会把「差量」与「基线」混在一起，归档时无从比对。

delta 的分节写法

分节标题 什么时候用 本 change 实例
## ADDED Requirements 本次新增的能力 本 change 的全部 Requirement 都是新增，所以只有这一节
## MODIFIED Requirements 主力规约里已有、本次要改的要求 本课没有——迭代 1 是第一次入库，主力规约还是空的
## REMOVED Requirements 本次要撤掉的要求 同上
## RENAMED Requirements 要求改名（较少用） 同上
每条 Requirement 写在 ### Requirement: 名称 下，正文用 MUST / MUST NOT 这类规范性动词；每条 Scenario 写在 #### Scenario: 名称 下，用 WHEN / THEN / AND 逐行给出可判定的步骤。唯一标准是：仅凭这条 Scenario，能否判定通过或不通过。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
改规约时改的是 delta，还是主力规约？ 只改 change 里的 delta。openspec/specs/ 归归档维护。 规约：只改 openspec/changes/<change>/specs/ delta，勿写 openspec/specs/
代码：git status 看本轮改动的路径
运行：openspec list --specs，归档前不应出现本能力
规约改动是否早于对应代码？ 是。先改规约再改代码，否则验收标准会随实现发生偏移。 规约：是否有该流程要求
代码：看提交顺序
运行：比较 delta 提交时间与代码提交时间
改完规约是否先校验再继续？ 是：先 openspec validate <change> --strict，确认格式与 Scenario 仍可判定。 规约：是否有该流程要求
代码：看本轮提交里是否含规约改动
运行：改完立即跑一次 validate

动手要做

  • 规约含糊或缺失时，用 /opsx-update（技能 openspec-update-change）修改 change 的 delta，不要直接编辑 openspec/specs/。
  • 改动只限于 openspec/changes/<change>/ 下的 Markdown；一并将 proposal.md 的 Non-goals 或 design.md 的 Decisions 补齐。
  • 改完先跑一次 openspec validate <change> --strict，再回到 Apply 循环继续实现。

3受阻情形分类与驳回方式

规约含糊先改规约，实现偏离引用 Scenario 驳回，环境问题按 README 从零复现。

知识点

三类受阻情形

规约含糊：先改规约再继续。实现偏离：引用 Scenario 驳回。环境报错：按 README 从零复现，复现失败再排查环境问题。

审查责任不转移

Harness（AI 编码代理）的产出仍由提交人负责。用隐藏按钮伪装权限控制、额外生成聊天界面，都属于范围蔓延（scope creep）。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
驳回生成物时是否引用 Scenario？ 引用规约原文驳回，而不是通过追加对话扩大范围。 规约：是否要求引用 Scenario
代码：回看对话记录中的驳回方式
运行：能否指出被驳回的实现违反了哪一条 Scenario
Harness 产出中是否出现范围蔓延？ 无：不用隐藏按钮伪装权限控制，不额外生成聊天界面。 规约：proposal.md「Non-goals（非目标）」
代码：搜新增路由、页面与依赖
运行：对照 Non-goals 逐项排除
规约含糊时先改规约还是先改代码？ 先改规约，再改代码；否则验收标准会随实现发生偏移。 规约：是否有该流程要求
代码：看提交顺序：规约改动应早于对应代码
运行：检查本轮 spec 提交时间是否早于代码提交

动手要做

  • 规约含糊先改规约。用隐藏按钮或切换角色伪装权限控制，引用 Scenario 驳回。

4开始 Apply 前：规约清晰度自检

把下面的问题发给 Harness，让它代为审查四件套。查出的问题回到 delta 修订；它没查出来的，责任仍在提交人。

可直接复制到会话中使用。以 change 目录（proposal.md、design.md、tasks.md、specs/auth-upload/spec.md）为审查对象，逐项给出文件与行号。

  1. 可判定性：对 spec.md 的每条 Scenario，各构造一个“满足”与一个“不满足”的具体行为示例；构造不出“不满足”示例的，说明该条不可判定，列出对应 Requirement 编号与原文。
  2. 术语一致性：列出四件套中的自定义术语、字段名与状态码，指出同一对象出现两种写法或相互矛盾的位置（例如同一响应时而 404 时而 403）。
  3. 响应语义：对规约中每个接口，检查是否写明成功与各失败分支的状态码及响应体要求；列出未写明的接口清单。
  4. 边界与异常：列出每条 Requirement 未覆盖的输入边界（空值、超上限、重复提交、并发），逐项判断属于 Non-goals 还是规约缺口，缺口单独列出。
  5. 任务覆盖：对照 tasks.md，指出哪些 Requirement 没有对应 task、哪些 task 缺少可执行的 verify 判据。
  6. 范围复述：用自己的话复述本次任务范围与 Non-goals，并列出你计划实现的路由与数据表清单；与 proposal.md 对照，指出超出与遗漏。

把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。
