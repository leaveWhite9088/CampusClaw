2 数据与种子

没有可区分的双班数据，后面的隔离无法验收。

每步按同一顺序展开：知识点 → 其他可行方案与选择依据 → 本步要核对 → 动手要做。“怎么查”一列给出三处证据：规约读哪条、代码搜什么、运行做什么；发现不一致，先补规约或改实现。全课汇总见 实现方案核对总表。

1表结构与租户列

一个实例、一个租户列：class_id 非空并建索引，这是后面所有隔离查询的地基。

知识点

单库多租户

在同一个 MySQL 实例中使用 class_id 划分班级。租户列必须非空并建立索引：非空约束防止出现无归属数据，索引支撑按班级的列表查询。这是第 4 课检索的前置条件。

其他可行方案与选择依据

方案 要点 本课如何取舍
一班一个 schema / 一个数据库 物理隔离更强。 代价过高。两班教学验收用单库 class_id 即可，也是常见的 SaaS 模型。
UUID 主键 vs 自增 ID UUID 可减少可猜测的枚举攻击。 本课用 404 隐藏资源存在性，自增也可。若用自增，更不能返回 403。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
class_id 是否非空并建立索引？ 非空 + 索引：非空防止无归属数据，索引支撑按班查询。 规约：是否写明字段约束要求
代码：看建表语句中的 NOT NULL 与索引定义
运行：尝试插入空 class_id 的记录，应被拒绝

动手要做

  • 建表：classes、users、materials、knowledge_entries、sessions。材料与知识库的 class_id 非空并建索引。

2可验证的种子数据

验收依靠对比：没有可区分的 A/B 两班材料，跨班失败路径就无法判定。

知识点

可验证的种子数据

验收依靠对比。若 A/B 两班材料的标题无法区分，就无法证明跨班访问失败。三类判定分别覆盖：教师可写、同班可读、跨班拒绝。

幂等初始化

种子数据可重复执行：第二次启动不得复制用户或材料，也不得覆盖教师已上传的内容。否则本地每次重启都会导致验收数据不一致。

其他可行方案与选择依据

方案 要点 本课如何取舍
手工改表、不写种子 准备数据最快。 否决。需要幂等初始化，重复启动不复制数据。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
种子是否幂等？ 重复启动不复制用户与材料，也不覆盖已上传内容。 规约：是否写明幂等初始化要求
代码：看种子实现方式：先查后插，还是无条件插入
运行：连续启动两次，比对用户与材料行数
A/B 两班材料标题是否可区分？ 可区分。不可区分就无法证明跨班访问失败。 规约：种子数据要求是否写明可区分
代码：看种子 SQL 中的材料标题
运行：用 B 班标题在 A 班列表搜索，应无结果
种子口令的来源与存储方式？ 来自环境变量，以 bcrypt 哈希存储。 规约：是否有口令管理要求
代码：看种子脚本中口令的处理方式
运行：查库确认口令字段为哈希值

动手要做

  • 种子班级 A / B；账号 teacher_a（教师，A 班）、student_a1（学生，A 班）、student_b1（学生，B 班）。口令只存 bcrypt，来源为环境变量。
  • 两班至少各有一条标题可区分的材料，并各关联一条知识库正文，便于跨班失败路径判定。
  • 种子幂等：重复启动不复制用户或材料，也不覆盖已上传内容。

3两条查询路径分开设计

列表使用 WHERE class_id = 会话班级；按 ID 取行不要在 SQL 里提前过滤，留给隔离步骤做先取行再校验。

知识点

列表过滤与按 ID 取行是两条路径

列表使用 WHERE class_id = 会话班级。按 ID 查询若在 SQL 中预先过滤掉跨班记录，跨班访问会返回空结果，无法与资源不存在区分，也不利于统一返回 404。先取行、再核对班级，语义才清晰。

其他可行方案与选择依据

方案 要点 本课如何取舍
ORM（如 GORM）替代手写 SQL 迁移与模型定义一体化。 可。本课不绑定 ORM；隔离条件必须显式，不能依赖隐式全局过滤器而不做验收。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
列表路径与按 ID 路径是否分开处理？ 列表带班级条件；按 ID 先取行再核对班级。 规约：是否写明这是两条独立路径
代码：搜按 ID 的查询语句，看是否提前过滤了班级
运行：按 ID 跨班请求，应得 404 而不是空对象

动手要做

  • 列表查询强制带班级条件；按 ID 取行不要在 SQL 中提前过滤班级，留到隔离步骤实现“先取行再校验”（fetch-then-check）。
