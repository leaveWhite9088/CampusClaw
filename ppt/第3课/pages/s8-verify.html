8 验收

主路径能够走通，失败路径有证据，才算完成迭代 1 的交付。

每步按同一顺序展开：知识点 → 其他可行方案与选择依据 → 本步要核对 → 动手要做。“怎么查”一列给出三处证据：规约读哪条、代码搜什么、运行做什么；发现不一致，先补规约或改实现。全课汇总见 实现方案核对总表。

1Verify：先过结构校验，再逐条判定 Scenario

验收对应 OpenSpec 的第四步。结构校验看规约立不立得住，行为校验看实现合不合规约，两层都要过。

知识点

校验分两层：结构校验与行为校验

结构校验看规约本身是否立得住：四件套是否齐全、delta 分节是否合规、每条 Requirement 是否至少有一个 Scenario、Scenario 是否写成可判定的形式。命令是 openspec validate <change> --strict，通过意味着「规约写得住」。

行为校验看实现是否符合规约：按 Scenario 逐条跑，判定通过或不通过。结构校验过了，不代表行为过了——一份格式完美但没实现的规约，validate 同样会通过。

两层都过，才算完成 OpenSpec 的 Verify 步骤，也才能进入归档。

本课必须逐条判定的 Scenario

Scenario（样板 change 命名） 怎么跑 判定标准
跨班按 ID 访问材料被拒绝 用 A 班账号请求 B 班材料的 ID 与文件 拒绝访问，响应不含 B 班标题、正文与存储路径
学生上传被拒绝（403） 用学生会话向上传接口提交一份合法文件 403；材料表、知识库表行数与上传目录均无变化
上传后知识库与列表可查 教师上传后用本班列表与查库各看一次 列表出现新条目，知识库有对应记录且归属本班
未登录访问受保护页面 清空 Cookie 后访问材料列表 页面跳登录页、接口返回未授权，响应体无任何材料数据
Scenario 名称以本人 spec.md 为准；上表是样板 change 里的关键几条，用于说明「判定」要落到哪一层。判定的结论（通过 / 不通过）要写进迭代说明，不能只说「已验过」。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
openspec validate 是否通过？ 通过：命令退出码为 0，且没有 error（警告也要读一遍）。 规约：tasks.md §9.8 与 specs/auth-upload/spec.md 结构
代码：本 change 目录
运行：openspec validate <change> --strict
关键 Scenario 是否逐条给出判定结论？ 逐条判定并留证：跨班被拒、学生上传 403、上传后列表可查。 规约：specs/auth-upload/spec.md R3.1 / R2.1 / R4.2 等 Scenario；tasks.md §9.4
代码：迭代说明里的判定记录
运行：按每条 Scenario 的命令重跑一次

动手要做

  • 运行 openspec validate <change> --strict，退出码为 0 且无 error 才算结构校验通过。
  • 按上表逐条跑关键 Scenario，把结论（通过 / 不通过）与命令输出写进迭代说明。
  • 校验通过后，把 tasks.md 收尾一节对应的条目勾上——勾选与 validate 的结果要一致。

2主路径：逐条留下证据

列表数据必须来自数据库查询；界面完备不能替代可复核的输出。

知识点

列表数据必须来自数据库查询

页面硬编码演示条目，第 4 课检索时会发现知识库是空的。本课就把从数据库查询作为验收条件。

其他可行方案与选择依据

方案 要点 本课如何取舍
只交成功路径录屏 演示效果好。 不够。安全需求靠失败路径证明。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
主路径是否逐条有证据？ 登录、上传、列表可见、学生只读四条各一份可复核输出。 规约：verify 条目清单
代码：看提交与迭代说明中的证据记录
运行：同伴按 README 复现一次
列表数据是否来自数据库？ 是。硬编码条目会在下一迭代的检索中暴露为空知识库。 规约：是否有该验收条件
代码：看列表接口的数据来源
运行：清空材料表后刷新列表，应无条目

动手要做

  1. 按 README 从零执行 Compose 启动，能打开登录页。
  2. 教师登录 → 上传 txt/md → 本班列表查询数据库可见新增条目。
  3. 同班学生可浏览、搜索、查看详情、下载；不能上传。
  4. Markdown 详情有格式化展示；浅色 / 深色、列表 / 网格视图可切换。

3失败路径：安全需求靠负向测试证明

三条失败路径要各有一条证据，并且证据能脱离本机复现。

知识点

负向测试

安全需求靠失败路径证明。只演示教师上传成功，证明不了学生被拒、跨班被拒。

证据可复核

命令输出或截图要让同伴能按同样步骤复现。口头确认通过，不构成质量门禁。

其他可行方案与选择依据

方案 要点 本课如何取舍
全部自动化 E2E（End-to-End，端到端）测试 可回归。 鼓励，本课不强制。最低要求是 curl 输出或截图可复核。
教师口头确认即可 课堂演示省时。 否决。同伴按 README 复现，互为证据。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
三条失败路径是否有证据？ 未登录、学生上传、跨班访问；至少两条有证据，建议齐全。 规约：失败路径要求
代码：搜 verify 中的负向用例
运行：逐条执行并保留命令与输出
证据能否脱离本机复现？ 可以：命令与输出一起留档，不依赖演示者口述。 规约：是否有证据可复核要求
代码：看证据是否含完整命令与上下文
运行：在另一台机器或干净目录重跑一次

动手要做

  1. 未登录访问材料接口：不返回业务数据。
  2. 学生上传：返回 403，数据库与磁盘状态不变。
  3. A 班账号访问 B 班材料 ID：取不到标题或正文（404）。

把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。

向 Harness 核对的参考提问

可直接复制到会话中使用。要求它逐项给出证据（文件与行号、命令与输出），找不到就明说、不许推测；回答只作线索，勾选前仍须亲自运行 verify 复核。

  1. 运行 openspec validate <change> --strict，贴出完整输出；如有警告，逐条解释含义与处理方式。
  2. 对照 spec.md 逐条列出 Scenario 的判定结论与证据（执行的命令与关键输出）；尚未运行的明确列出，不得跳过。
  3. 检查 tasks.md 是否还有未勾选项，逐项说明原因；勾选与实际运行结果是否一致？
  4. 起草迭代说明中的验收结论段：每条关键 Scenario 给出“通过或不通过 + 证据”，我来复核措辞。
