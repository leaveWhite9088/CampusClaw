3 登录与会话

登录成功后建立服务端会话（session）。会话中缺失的属性，服务端后续无法补齐，相关需求即不可判定。

1会话要承载什么，放在哪里

认证只回答“你是谁”；会话要能判定 user_id、role、class_id，而这三项不交给客户端保管。

知识点

认证不是授权

认证证明你是某个账号。授权决定教师能否上传、学生能否只读。先认证再授权。会话至少能判定 user_id、role、class_id。

服务端会话与 Cookie 属性

会话 ID 是不透明随机串，放在 HttpOnly Cookie 里。浏览器自动带上，脚本读不到。SameSite=Lax 限制跨站带 Cookie。角色与班级每次从用户表读取，不采信客户端回传。

其他可行方案与选择依据

方案 要点 本课如何取舍
argon2 替代 bcrypt 抗 GPU 并行破解能力更强。 可。不要用 MD5/SHA 无盐哈希。
SameSite=None; Secure 跨站嵌入需要。 本课同源，Lax 足够。本机 HTTP 环境不要强制设置 Secure 属性，否则浏览器会拒绝写入 Cookie。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
会话中是否具备 user_id、role、class_id 三项？ 三项齐备；缺任一项，后续授权与隔离需求都不可判定。 规约：specs/auth-upload/spec.md R1 与 design.md D2（会话字段）
代码：看 sessions 表结构与会话读取逻辑
运行：登录后调 /api/me，检查返回内容

动手要做

  • POST /api/login：bcrypt 校验；成功后签发新会话，旧会话作废，防止会话固定。
  • Cookie：HttpOnly、SameSite=Lax。

2登录、登出与会话固定

登录换发新 ID、登出删服务端会话行——这两件事决定登录态能否立刻失效。

知识点

会话固定

登录成功必须签发新 ID，并作废登录前的会话。否则攻击者可诱使受害者使用已知的会话 ID，待其登录后共用同一会话。

默认拒绝

仅重定向到登录页不够。受保护 API 必须 401，且响应体不得含标题、正文、路径。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
登录成功是否换发新的会话 ID？ 换发并作废登录前的会话，防止会话固定。 规约：是否有防会话固定要求
代码：看登录 handler 的会话写入位置
运行：对比登录前后的 Cookie 值是否变化
Cookie 属性是否为 HttpOnly、SameSite=Lax？ HttpOnly + SameSite=Lax；本机 HTTP 环境不加 Secure。 规约：是否写明 Cookie 属性
代码：看 Set-Cookie 的构造代码
运行：浏览器开发者工具查看 Set-Cookie 头
未登录访问受保护接口返回什么？ 401，且响应体不含标题、正文与磁盘路径。 规约：未登录失败路径 Scenario
代码：搜鉴权中间件与分支
运行：清空 Cookie 后调 /api/materials
登出后旧 Cookie 是否失效？ 401，服务端会话行已删除。 规约：登出 Scenario
代码：看 logout handler
运行：登出后用旧 Cookie 再请求一次

动手要做

  • 未登录访问受保护页面引导到登录页；调用受保护接口返回 401，响应体不得含材料标题或正文。
  • POST /api/logout 删除服务端会话并清 Cookie；再用同一 Cookie 必须 401。

3防枚举、限流与方案边界

用户不存在与口令错误必须无法区分；同时明确本迭代不引入 JWT。

知识点

账号枚举与限流

用户不存在与口令错误若返回不同文案或耗时，可被用来探测账号。统一提示文案，并对用户名 + IP 组合做限流。锁定期的响应仍与凭据错误一致，避免 429 本身成为账号枚举的依据。

为什么不用 JWT / Bearer token

本迭代是浏览器同源站点，不是开放 API 或移动端。JWT 常被存入 localStorage，脚本可读，一旦出现 XSS（跨站脚本）漏洞即被窃取；载荷里的 role / class_id 容易被当成授权依据。登出时服务端删会话行即可立刻失效；无状态 JWT 在过期前很难作废，还要引入黑名单，等于又回到服务端会话模式。OAuth / SSO（单点登录）属于联邦身份（Federated Identity）体系，超出本课范围。Cookie 里的会话 ID 也是一种 token，只是不把权限声明交给客户端保管。

其他可行方案与选择依据

方案 要点 本课如何取舍
JWT / Refresh / OAuth 见认证方案对照页。 了解机制与代价。本课选会话 Cookie：同源、可立刻登出、班级信息不放入客户端载荷。
Redis 存会话与限流 多副本共享状态。 本课单实例、会话在 MySQL 即可。多副本再引入共享存储。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
失败提示与耗时是否统一？ 账号不存在与口令错误返回一致，并做等价耗时的哈希比较。 规约：是否写明统一失败响应
代码：搜错误分支与哈希比较的位置
运行：两种输入各试一次，比状态码、响应体与耗时

动手要做

  • 失败提示统一，不区分用户不存在与口令错误。用户不存在时也做一次等价耗时的哈希比较。
  • 对用户名 + IP 做失败限流；锁定期内即使口令正确也拒绝，响应仍与凭据错误一致。
  • 不要签发 JWT，也不要把会话 ID 或角色写进 localStorage。其他方案见 认证方案对照，本课只实现会话 Cookie。
  • GET /api/me 返回当前角色与班级，供前端决定是否渲染上传入口。

把否决理由用自己的话写进 design / 迭代说明；原文照录本表不算 ADR。

向 Harness 核对的参考提问

可直接复制到会话中使用。要求它逐项给出证据（文件与行号、命令与输出），找不到就明说、不许推测；回答只作线索，勾选前仍须亲自运行 verify 复核。

  1. 找到登录成功的处理代码：会话写入了哪些字段？user_id、role、class_id 是否齐备？贴出文件与行号；若缺项，明确说未实现。
  2. 登录成功是否换发新会话 ID、登录前的旧 ID 是否作废？指出对应代码；找不到换发逻辑就直说，不要推测。
  3. 列出 Set-Cookie 的全部属性与会话中间件的校验逻辑：角色与班级是每次从用户表读取，还是采信客户端回传的值？
  4. 实际调用登出接口后携旧 Cookie 请求受保护接口，贴出响应；再对比未登录、口令错误、触发限流三种失败的响应是否同形。
