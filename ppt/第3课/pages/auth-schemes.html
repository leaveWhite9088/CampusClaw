知识点

JWT（JSON Web Token）

由三段组成：头部（Header）、载荷（Payload）、签名（Signature）。载荷可携带 user_id、role、exp 等声明。校验签名即可承认身份，服务端不必每请求查会话表，利于无状态水平扩展。代价：载荷默认可见（Base64 编码不是加密）；将 role 写入 token 后，修改角色需等 token 过期；登出不能立刻作废，除非额外维护黑名单，相当于又把状态管理引回服务端。

Access token 与 Refresh token

短期 access token 用于调用 API，长期 refresh token 用于换取新的 access token。降低令牌泄露后的可用窗口，并可通过 refresh 轮转检测盗用。实现复杂度高：存储、轮转、重放、吊销。本课单实例浏览器应用不需要这套。

OAuth 2.0 / OIDC / SSO

把登录委托给学校的 IdP（Identity Provider，身份提供方）或 GitHub 等。OAuth 2.0 负责授权，OIDC（OpenID Connect）在其之上增加身份认证层。适合多系统共用校园账号。本课要练习的是自己系统内的会话管理、RBAC（Role-Based Access Control，基于角色的访问控制）与班级边界，不接入外部身份。

API Key

给机器调用的长期密钥，通常放在请求头。没有浏览器会话、没有登录页。适合脚本与对内服务，不适合教师与学生交互，也难以按用户吊销，无法支撑班级隔离。

2本课的选择：服务端会话 Cookie

同源浏览器站点、登出可立刻失效、角色与班级不放进客户端载荷——这三条决定了本课的技术选型。

知识点

不透明会话 ID

服务端保存会话行，客户端只持有随机 ID。登出删除会话行即失效；角色与班级每次从数据库读取。传输可以走 Cookie（本课），也可以走 Authorization 头，后者需要前端自行存储并附带，容易落入 localStorage。

Cookie 与 CSRF / XSS

Cookie 会被浏览器在同站请求里自动带上，要防跨站伪造（CSRF）：同源、SameSite、必要时 CSRF token。JWT 放请求头不会自动跨站带出，CSRF 风险面小，但若存入 localStorage，一旦出现 XSS（跨站脚本）漏洞即可被读走。这是一个典型的权衡（trade-off）：Cookie 方案主要面临 CSRF 风险，客户端存储 token 主要面临 XSS 风险。

本课为何选会话 Cookie

  • 前后端同源，Nginx 反向代理 /api，Cookie 自动带上，前端无需自行保管 token。
  • 班级隔离要求每次以服务端身份为准；JWT 载荷中的 class_id 容易诱使实现去信任客户端数据。
  • 验收包含登出后 401；会话删行即可判定，JWT 还要额外讲黑名单。
  • 当前单实例。多副本与无状态 JWT 的取舍放到后续部署课，不要提前换方案。
