实现方案核对总表

本课只做 CampusClaw 迭代 1。各步骤页内已内置“本步要核对”清单；本页把全部 91 项决策点汇总在一起，供整课核对与打印：每一项到底用了哪个方案、落在哪一层、怎么验证。核不通过的，先补规约或改实现，再继续下一步。

用法：每学完一个步骤，回到这里找到对应小节，按“怎么查”一列的三处证据逐条核对，通过的逐项勾选。文档与代码两侧不一致（例如文档写 404、代码返回 403）同样视为不通过——它会在下一迭代暴露为不可判定的需求。

OpenSpec 演示 change：openspec/changes/add-auth-rbac-class-knowledge/（四件套：proposal.md、design.md、tasks.md、specs/auth-upload/spec.md）。规约列中的路径均相对于该目录，除非写明 openspec/specs/。

要做成什么样　范围与角色权限打开该页

核对项本迭代应采用怎么查（规约 / 代码 / 运行）自检
角色与能力边界是否逐条写成可判定的要求？教师＝上传/查看/下载；学生＝查看/下载。多给一项能力就多一个垂直越权面。规约：specs/auth-upload/spec.md R2、R4、R5
代码：搜角色常量与权限判断分支，看学生分支是否出现写操作
运行：分别用教师与学生账号各试一次上传
超级管理员是否被明确列为本迭代不做项？已列入。它是产品完整形态里必然存在的角色，但跨班可见，会与“跨班返回 404”的隔离验收冲突；隔离稳定后单独开一次变更设计它的越权路径与操作审计。规约：proposal.md Non-goals「平台超级管理员」与 R2 仅 teacher/student
代码：搜角色常量与查询分支，看是否有 admin 或可跨班的查询
运行：查 users 表 role 取值，只有 teacher / student
班级边界是写进规约，还是只写在 design 里？必须作为 Requirement 的 Scenario 出现，隔离失败才有判定依据。规约：specs/auth-upload/spec.md R3 各 Scenario（非仅 design prose）
代码：对比 spec 与 design 中 class 边界表述
运行：按 Scenario 逐条跑失败路径，看是否都能判通过与否
Non-goals 是否写明检索、问答、作业不做？必须写明。缺失时 Harness 最容易越界生成整块功能。规约：proposal.md「Non-goals（非目标）」
代码：搜依赖清单与路由，看有无向量库、对话接口
运行：让 Harness 复述范围，观察是否夹带不做项
最小 UI（R9）是否在 spec 中可判定？两页、/api/me、详情/下载 API、401 回登录、R9.6 防脚本；R9.7 筛选可选。规约：specs/auth-upload/spec.md R9
代码：对照 tasks §7
运行：按 R9 Scenario 浏览器走查一遍
列表与搜索的数据来源是否写明？必须来自按班级过滤的数据库查询，不得硬编码演示条目。规约：specs/auth-upload/spec.md R3.3、R4.1
代码：搜列表 handler，看查询语句是否带 class_id
运行：清空材料表后刷新列表，应无任何条目
上传校验与失败状态是否可判定？扩展名、大小、内容三类失败各有明确状态码，且数据库与磁盘无残留。规约：specs/auth-upload/spec.md R4.4–R4.7
代码：搜校验分支与错误返回位置
运行：分别上传 .exe、超限文件、非法编码文件各一次

请求链路是否只有一条（浏览器 → Nginx → Go → MySQL）？前端不直连数据库，任何数据访问都必须经过 Go。规约：design.md「Decisions / 接口一览」

运行：停掉 api 容器，前端应整体不可用而非仍能读数据

代码：搜 nginx.conf 中的 location / alias 配置
运行：直接请求 /uploads/<猜测文件名>，应取不到文件
数据库有没有映射到宿主端口？只在 Compose 内部网络可达，不映射 3306。规约：design.md「配置与启动」/ Compose 网络
代码：看 docker-compose.yml 中 db 服务的 ports
运行：本机尝试连接 3306，应连不上
/api 是否同源反向代理，开发与生产路径是否一致？同源；开发时 Vite 代理路径与生产 Nginx 保持一致。规约：design.md D1；specs/auth-upload/spec.md R1.1
代码：对比 vite.config 与 nginx.conf 的代理路径
运行：开发环境与 Compose 环境各调一次 /api/me
接口清单与规约是否一一对应？路径、鉴权要求、跨班返回码三者一致，无多出或少掉的接口。规约：design.md「接口一览」↔ specs/auth-upload/spec.md R1–R5
代码：搜路由注册表，与规约逐条比对
运行：对每个接口各跑一次未登录与跨班请求

安全与部署　口令、密钥与探测端点打开该页

核对项本迭代应采用怎么查（规约 / 代码 / 运行）自检
口令是以哈希形式保存的吗？bcrypt 加盐慢哈希；不存明文，也不用可逆加密。规约：specs/auth-upload/spec.md R7.1–R7.2；design.md D5
代码：搜明文赋值与哈希调用位置
运行：直接查 users 表，看口令字段形态
会话密钥与数据库口令来自环境变量吗？只来自环境变量；缺失则启动失败，无内置默认值。规约：specs/auth-upload/spec.md R7.3、R7.5
代码：搜默认值常量与 os.Getenv / process.env 读取点
运行：删掉 .env 后启动，应失败而非照常启动
/health 是否混入数据库探活？只做存活判定；数据库不可用由业务接口返回 503，不判为会话失效。规约：design.md D9；specs/auth-upload/spec.md R8.3、R8.6
代码：看 health handler 是否查询数据库
运行：停掉 db，对比 /health 与 /api/materials 的返回
三类失败响应是否同形？账号不存在、口令错误、被限流三类返回一致，不成为账号枚举的依据。规约：specs/auth-upload/spec.md R1.2、R1.3、R1.4
代码：搜错误返回分支，看是否有差异化文案
运行：三种输入各试一次，对比状态码、响应体与耗时
密钥有没有进过仓库历史？无。若曾提交，必须轮换而不是只删提交。规约：specs/auth-upload/spec.md R7.4
代码：git log 检索密钥关键字
运行：克隆一份仓库到干净目录，全局搜密钥

认证方案对照　登录态到底放在哪打开该页

运行：登录后看浏览器存储面板与响应头 Set-Cookie

运行：改一次角色后立即请求，看是否仍按旧角色放行
