系统怎么走

前后端分离。浏览器只访问 Nginx；数据库不要映射到本机端口。

1请求链路：浏览器 → Nginx → Go → MySQL

只有一条链路，信任边界落在 Go；浏览器与静态页一律不可信。

知识点

信任边界在 API

浏览器与静态页不可信。认证、授权、隔离、上传校验全部发生在 Go。Nginx 只托管前端静态资源，并将 /api 反向代理到 Go 后端，不得将上传目录作为静态资源目录暴露。

同源与反向代理

前端通过同源 /api 调用后端，避免跨域请求带来的 Cookie 作用域与 SameSite 策略问题。开发时 Vite 的代理路径应与生产环境 Nginx 保持一致。

其他可行方案与选择依据

方案 要点 本课如何取舍
服务端渲染单体（模板 + 同进程） 页面与接口一体，Cookie 简单。 可行，但当前需求是前后端分离。若第 2 课 design 已写成单体，先改规约或按 design 实现并写清差异。

动手要做

  1. 浏览器访问 Nginx 提供的前端页面（默认 http://localhost:8080）。
  2. 前端通过同源 /api 调用 Go。
  3. Go 负责认证、授权、班级隔离和材料处理。
  4. MySQL 保存用户、班级、会话、材料与知识库正文；原文件放服务器上传目录，只挂在 api 上，不要经 Nginx 静态暴露。

2攻击面最小化：数据库与上传目录不外露

不映射数据库端口、不把上传目录当静态站，是最省成本的默认拒绝。

知识点

攻击面最小化

db 只在 Compose 内部网络。对外只暴露 web 端口。能扫到的端口越少，越权探测的入口越少。

其他可行方案与选择依据

方案 要点 本课如何取舍
数据库映射到本机 3306 便于用图形化客户端连接数据库排障。 否决作为默认。扩大攻击面；查询数据库时通过 compose exec 进入容器执行。

本步要核对

数据库有没有映射到宿主端口？ 只在 Compose 内部网络可达，不映射 3306。 规约：design.md「配置与启动」与 Compose 网络约定
代码：看 docker-compose.yml 中 db 服务的 ports

3技术选型与接口清单

选型表与接口表是规约的对照面：接口签名必须与规约逐条对应。

知识点

这套技术栈都是主流技术

本迭代每一项选型都是各自位置上使用最广、资料最多的选择，遇到问题在官方文档与社区能找到现成答案：

  • 前端：React 18 + TypeScript + Vite，当前前端工程的主流组合（组件化、静态类型、构建工具）。
  • 后端：Go + 标准库 net/http，不引入 Web 框架，把需要评估的变量降到最低。
  • 数据库：MySQL 8.0，使用最广的关系型数据库，本机与云上都容易获得。
  • 入口与部署：Nginx（最主流的反向代理与静态资源服务器）+ Docker Compose（单机多容器编排的通用入口）。

本课重点是访问控制与数据隔离，不在选型上做冷门尝试：方案越主流，越能把注意力放在“谁能看到什么数据”上。

其他可行方案与选择依据

方案 要点 本课如何取舍
Flask + SQLite（第 2 课示例的常见技术栈） 本地部署轻量，无需独立的 db 容器。 当前需求用 Go + MySQL，为后续检索与多连接做准备。SQLite 的文件锁与 Compose 环境等价性较弱。

本步要核对

核对项 本迭代应采用 怎么查（规约 / 代码 / 运行） 自检
接口清单与规约是否一一对应？ 路径、鉴权要求、跨班返回码三者一致，无多出或少掉的接口。 规约：design.md「接口一览」逐条对照 specs/auth-upload/spec.md R1–R5
代码：搜路由注册表，与规约逐条比对
运行：对每个接口各跑一次未登录与跨班请求
