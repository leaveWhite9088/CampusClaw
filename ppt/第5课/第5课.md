# 第 5 课：提示词、AI 技能与流式会话

> 来源：北京大学《互联网软件开发技术与实践》第 5 课课件（HTML 整理为 Markdown）

---

## 本课概述

本课做一个解题助手智能体。学生就题目提问时，助手先确认身份与班级，再加载提示词、选择技能、检索本班知识库，然后生成回答。提示词、知识库、技能都要参与同一次回答。

### 1. 本课承接第 4 课

登录、角色校验、上传入库和本班检索沿用前两课。知识库已经能按班级检索并标出出处，本课把它接到助手的行动里，不再单独做一个检索页。

### 2. 一次提问怎么走完

#### 提示词规定助手是谁

提示词由教师编写并保存，从下一轮对话生效。它说明助手的角色，不负责某一类题目的解题规程。学生不能修改提示词。

#### 技能规定这一题怎么导

本课实现解题引导。开启时给思路、引用本班材料的标题和位置，不直接给出最终答案。关闭后，同一问题的回答方式应当明显不同。学生不能开关技能。

#### 知识库提供可回溯的依据

选定技能之后，再检索本班材料。命中则在回答中标出出处；没有命中则说明资料中未找到，不编造出处。班级只从登录会话读取。

### 3. 本课范围

#### 本课要做成

一个学生能连续追问的解题助手。同一次回答必须用上已保存的提示词、已启用的解题引导，以及本班知识库的检索结果。回答按会话保存，并以服务器推送事件（SSE）逐段返回。

#### 本课不做

作业提交、作业批改、错题讲解、异步队列，以及关怀式对话，都不进入本课验收。另外两项技能留到后面的课。

### 4. 先读一篇：业界的技能怎么做

动手前先看全景。业界把"让模型干活"的技术分成四层：Function Calling、Tool、MCP、Skill；技能靠渐进式披露控制在上下文里的开销。本页逐项对照业界机制与本课取舍，并给出往完整教学智能体扩展的路径。

## AI 技能：业界全景与本课取舍

本课实现解题引导这一个技能。在动手之前，先看工业界怎么做"技能"：把业界机制摊开成四层，再对照说明本课为什么只取其中一小块。读完后应当能回答两个问题——业界的技能是怎么被加载的，本课的裁剪省掉了什么、为什么可以省。

### 1. 业界的四层技术栈

当前让大模型干活的主流技术，可以自下而上放进四层里。它们不是四个互斥的选项，而是上下依赖的关系。

1. **1 模型层 · Function Calling**：模型原生能力：按工具描述生成结构化调用请求
2. **2 能力层 · Tool**：原子执行函数，一次调用做一件事，建立在函数调用之上
3. **3 协议层 · MCP**：开放协议，标准化工具的发现与连接，一次开发处处可用
4. **4 场景层 · Skill**：封装领域知识与多步流程，内部可编排多个工具

| 层 | 名称 | 职责 | 代表 |
| --- | --- | --- | --- |
| 模型层 | Function Calling | 模型根据工具的名称、参数说明，输出一次结构化的调用请求；执行仍由应用侧完成 | OpenAI Tools API、Claude Tool Use、Gemini Function Calling |
| 能力层 | Tool | 把查数据库、发消息、执行脚本等操作封装成单个可调用函数 | LangChain Tools、OpenAI Agents SDK Tools |
| 协议层 | MCP（Model Context Protocol） | 统一工具如何被注册、发现与调用；应用接入一次，即可使用全部兼容工具 | Anthropic 于 2024 年底开源，主流模型与编辑器已跟进 |
| 场景层 | Skill | 把某类任务的完整做法写成指令与脚本，供模型按需加载执行 | Claude Agent Skills、各平台的技能市场 |

> MCP 并不替代 Function Calling。MCP 标准化的是工具的供应方式：应用把协议里登记的工具定义翻译成模型认识的调用格式，再交给模型选择。模型每次经 MCP 调用工具，本质上仍是一次函数调用。

### 2. 技能如何被加载：渐进式披露

一个平台可以装几百个技能而不撑爆上下文窗口，靠的是分三层加载——每一层都比上一层大，但只在需要时才读入。

> 渐进式披露：常驻的只有一句简介，完整指令与参考文件按需加载。装几百个技能的常驻成本，只是第一层的索引开销。
> 图中标注：学生提问 / 进入助手 / 判断需要哪个技能 / 依据是每个技能的一句话简介 / 第一层 · 元数据常驻 / 约 50 token / 技能名称与一句话简介，每一轮对话都在上下文里 / 第二层 · 技能全文 / 约 500 token / 被选中的技能才读入完整指令（SKILL.md 全文） / 第三层 · 引用文件 / 2000+ token / 技能内提到的脚本、参考文档，执行到那一步才读取

#### 技能是一个文件夹，不是一段代码

以 Claude Agent Skills 为例，一个技能是一个文件夹：一个 `SKILL.md`（开头写名称与简介，正文写完整指令），加上可选的 `scripts`（脚本）、`references`(参考文档) 与 `assets`(模板资源)。文件夹可用 Git 做版本管理，也能直接复制分享——因此写技能不限于工程师。

#### 确定性逻辑写成脚本，不靠模型现场推理

格式转换、对账这类步骤固定的操作，业界做法是写成 Python 或 Bash 脚本放进技能里，模型按文档引用去执行。脚本自带说明、可以修改、不占常驻上下文。原则是：能用代码的，不用模型推理。

#### 技能也是攻击面

技能提供的是"指令"，模型会照做。一个恶意技能可以借指令诱导模型读写文件、外发数据；技能引用的外部网页也可能夹带注入指令。因此装技能前要审查其脚本的网络访问与文件操作，外部来源的技能尤其要谨慎。

### 3. 业界机制与本课取舍

本课是教室里的单一应用，链路固定、角色明确，因此只取四层技术栈中的一小块。逐项对照如下。

| 业界机制 | 本课对应 | 取舍说明 |
| --- | --- | --- |
| 系统提示词常驻 | 教师保存的提示词 | 由教师编写、全班共用，从下一轮对话生效；学生不可修改。职责是规定助手是谁，不负责具体题型的解题规程 |
| 技能触发加载 | 解题引导技能 | 本课只有一个技能：启用时把解题引导的说明整段注入；开关由教师控制，学生不能自行开闭 |
| 模型自主选择工具 | 本班知识库检索 | 检索沿用第 4 课的实现，固化在服务端流程里：先选技能、再检索，不交给模型临场决定调不调 |
| MCP 协议 | 暂不引入 | 工具（检索、提示词、技能开关）都在同一个应用内，不需要跨应用共享，引入协议只增加复杂度 |
| 子代理与编排 | 暂不引入 | 单轮问答的链路固定：确认身份、加载提示词、选择技能、检索、生成。不存在需要多代理协作的分支 |

> 本课的另一主题流式会话（SSE）不属于技能机制，但同为业界 Agent 的标准组件：回答由服务器逐段推送，减少首字等待。技能决定"答什么、怎么答"，流式决定"怎么送达"，两者在链路上互不影响。

### 4. 往完整教学智能体扩展的路径

本课走通"提示词、技能、知识库三者参与同一次回答"之后，如果要把系统扩展成更完整的教学智能体，业界四层就是现成的路线图。

#### 把技能文件夹化

解题引导目前是服务端的一段配置。扩展时可改写成业界通用的技能文件夹格式：元数据（名称、适用条件）+ 指令（引导规程）+ 脚本（如画图、验算）。错题讲解、作业批改两项后续技能按同一格式新增，服务端只要维护一个技能注册表。

#### 加载策略从整段注入过渡到渐进式披露

技能少时，启用了就整段注入，简单可靠。技能增多后，改为常驻只放一句话简介，按学生的问题命中技能再加载全文——这正是第二层与第三层的做法，可以按 token 预算逐步引入。

#### 权限与留痕先于能力扩展

教学场景的边界比能力更重要：学生不可修改提示词、不可开关技能，这些规则要落在服务端而不是提示词里；每次技能选择、每次检索命中都留痕，管理员可回溯某次回答用了哪个技能、引了哪些材料。

#### 为技能建立评测集

技能一多，"选没选对技能、答得是否符合该技能的规程"就需要量化。做法与第 4 课验证检索质量类似：积累一批典型题目与期望行为，改动技能说明后回归评测，防止改一处、坏一片。

> 扩展顺序建议：先多技能注册表，再渐进式披露，最后才考虑协议化（MCP）。与业界选型口诀一致——简单场景不过度设计，复杂场景不过度简化。
